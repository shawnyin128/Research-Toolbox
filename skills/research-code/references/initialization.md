# Initialize a Research Repository

1. Inspect existing files, instructions, Git state, dependencies, data locations, and runtime. Even an apparently new directory may contain user work. Infer project/package/CLI identity from the request; do not carry identities from a source project.
2. Choose only responsibilities needed now. Use the [SAI flat layout](structures/sai.md) by default, or the [namespaced package](structures/package.md) for an established/requested package layout. Both retain central `hparam` and same-named composition entries. External data and run outputs may live outside the repo. Integrated processing belongs with maintained code. A directory named `data` is not sufficient reason to ignore its scripts.
3. For a new Python project without another constraint, use uv, an installable package and a console entrypoint. Respect the actual compatible Python range; do not upgrade interpreters or drivers as a side effect. Declare dependencies and development tools, generate the lockfile through the resolver, and use `.venv`. See [uv project files](https://docs.astral.sh/uv/concepts/projects/layout/) for the tool's project/lock/environment semantics.
4. Keep one authoritative set of project instructions. Adapt [AGENTS.md.template](../assets/AGENTS.md.template) and, when relevant, [CLAUDE.md.template](../assets/CLAUDE.md.template). Preserve existing research/runtime rules. Substitute tokens, render any referenced docs, and check that links remain valid outside the skill installation.
5. Implement only requested working capabilities. A skeleton can expose help/version; do not advertise train/evaluate commands with no implementation. Apply [SAI conventions](sai-conventions.md) by default and record the selected structure guide and any explicit project constraints.
6. Verify the actual dependency workflow, imports and CLI outside the repository, then run relevant behavioral tests/lint/format checks. A source-tree import succeeding is not proof the package installs correctly. Record missing runtime/dependency checks rather than inventing passes.

For an existing repository, retain its working stack unless environment migration is requested or needed for the task. Preserve package indexes, accelerator builds, extras, public commands, and scientific defaults. Avoid replacing mature metadata with a blank template.

Use precise ignores for environments, caches, secrets, raw data, and run artifacts. Keep code, tests, configuration, curated reports, and their assets versioned. Discover plugin support by actual content/consumers; do not ignore an entire mixed directory based on its name.
